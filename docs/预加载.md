# 预加载（资源调度与兜底）

`preload.js` 中的 `AliceADVPreload` 模块负责三件事：把即将用到的资源提前取回浏览器缓存、在进入舞台时用遮罩等到关键资源就绪、以及在资源确实来不及时就地兜底。

预加载贯穿整局游戏，不是只在进入网页时做一次。本文说明整套机制的原理；配置项的定义、取值与默认值见 `信息配置.md` §5。

| 关注点 | 位置 |
|---|---|
| 配置（`boot` / `runtime` / `lookahead` / `chapter` / `stage` / `fastForward` / `fallback` / `timeout` / `onTimeout` / `slowSpeedKBps`） | `info.json` 的 `preload` 字段，见 `信息配置.md` §5 |
| 实现 | `aliceadv/src/aliceadv/template/style/preload.js` |
| 编译期资源清单 | `builder.py` 的 `collect_asset_sizes()` → 产物内联 `window.__ASSETS__` |
| 遮罩 DOM 与样式 | `template/index.html`（`#boot-mask` / `#wait-mask`）、`template/style/preload.css` |
| 调用方 | `index.html` 的 bootstrap、`style/engine.js`、`style/script.js` |
| 静态不变量 | `aliceadv/tests/test_preload_order.py` |
| 时间轴行为测试 | `aliceadv/tests/test_preload_plan.py`（在 node 里真正调用 `plan()`） |

## 1. 概念模型

| 概念 | 职责 | 在引擎中的实现物 |
|---|---|---|
| 章（Chapter） | 剧情组织单位，同时是预加载的**搜索上界** | `story/chX.json` 一个文件；文件内两层结构时取当前子章 |
| 句（Line） | 时间轴刻度 | `say` / `narrate` / `title` / `decide` / 无参 `pause` 这些阻塞指令 |
| 资源（Resource） | 调度对象 | `bg` / `show` / `sprite` / `music` / `sound` / `voice` 的 `src`，`say.voice`，角色对话框 |
| deadline | 该资源第一次被使用的时间，单位为「相对当前时刻的秒数」 | 时间轴遍历累加得到 |
| slack | `deadline − 预计下载耗时`，升序决定下载顺序 | 每次推进重算 |
| 兜底（Fallback） | 资源未就绪时的动作 | 指令执行前的 `barrier()` |

调度的一次完整流转：

```
advance()  →  hookPredict()  →  plan()  →  按 slack 排序  →  队列  →  浏览器
   │                              ↑
   │                        实测每句耗时 + 编译期资源体积
   └→  barrier(c)  →  未就绪且策略为 block  →  #wait-mask  →  就绪后继续执行 c
```

## 2. 出发点：五个事实

这套机制的全部规则都是从下面五条约束推导出来的。

### 2.1 同源并发连接约 6 条，且按发起顺序排队

浏览器对同一源（协议 + 主机 + 端口）只维持约 6 条并发连接。超出的请求进入等待队列，并**按发起顺序**依次获得连接。

推论：**入队数组的顺序就是下载顺序，也就是优先级**。把资源交给队列的顺序，是这套机制唯一能控制的东西。`preload.js` 用 `pump()` 作为唯一的发起入口，默认并发窗口 `CONCURRENCY = 4`。

### 2.2 「下载完成」不等于「可以立即绘制」

图片数据下载完成后还要解码成位图。浏览器对已解码位图的缓存是弱引用，内存吃紧时会被回收；回收之后再次绘制需要重新增量解码，观感就是图片自上而下「逐行扫出来」。

推论：外壳图（对话框、面板边框、按钮、占位图）这类**每个页面都要用、数量有限**的图，在预加载阶段就主动解码并长期持有引用（`retained`，上限 64 张）。剧情背景与立绘可达上百张，不常驻解码位图，避免内存膨胀。

### 2.3 脱离 DOM 且未播放的媒体元素会被中止

`new Audio()` 加 `preload="auto"`，如果元素不在 DOM 中又没有调用 `play()`，浏览器会把它当作无人使用的预取并**中止请求**（`ERR_ABORTED`）；把 `src` 置空则是主动中止。

推论：`http(s)` 下改用 `fetch(url)` 预取音频，并**读完响应体**——响应体被读完才会真正落进 HTTP 缓存。`file://` 下 `fetch` 受限，回退到媒体元素。

同类陷阱：下载中的 `Image` / `Audio` 如果只被局部变量引用，垃圾回收可能在下载途中回收它并中止请求，表现为「发起过却永远没完成」。`preload.js` 用 `inflight[]` / `audioHold[]` 持有在途对象直到加载结束。

### 2.4 资源体积在下载前不可知

浏览器不提供「这个文件多大」的查询方式，而调度需要把它换算成「预计还要下多久」。

推论：体积由**构建时**统计并内联进产物（见 §3）。运行时只读这份清单，不发额外请求。

### 2.5 「取回过一次」不等于「现在取得到」

预加载能做的只是**发起一次请求并把响应留给浏览器**；之后这份响应还在不在缓存里，由缓存层决定，引擎无从干预：

| 情况 | 结果 |
|---|---|
| 缓存条目仍在 | 用的时候直接命中，几毫秒可用 |
| 缓存条目被淘汰（本项目 138 项 / 153 MB，位图与编码数据都可能被回收） | 用的时候重新联网 |
| 响应不可缓存（缺 `Last-Modified` / `Cache-Control` 的服务器） | 从头到尾都不会留下缓存 |
| DevTools 勾了「禁用缓存」（调试时的常见状态） | 磁盘缓存的读被绕过，用的时候多半要重新联网（间隔很小时仍可能被复用，见 2.6） |

推论：**判断「这个资源现在能不能用」，不能查「我们预加载过没有」，只能真的取一次。**

实测（背景 `g1_2.png`，先不限速预载、中途开 Slow 3G 限速）：

| 缓存状态 | 显示该背景时的请求 | 观感 |
|---|---|---|
| 可用 | 命中磁盘缓存，同刻完成 | 正常 |
| 禁用缓存（且预载与显示间隔 33 秒） | 重新联网，**15.5 秒后才下完** | 半张图（上已绘制、下露底色），且全程没有转圈圈 |

第二行就是「低网速下背景逐行扫描、看不到等待遮罩」的根因：当时的就绪判据是「我们预载过一次」，它一直是 `done`，于是 `barrier()` 判定「已就绪」直接放行。修复方式是 `barrier()` 改用**可绘制性探针**（见 §6.5）。

### 2.6 预加载、缓存、绘制是三件事（不要混为一谈）

- **预加载**：发起请求、响应到达。产出是**一次传输**。
- **缓存**：浏览器是否**留着**那份响应。由 `Cache-Control` / `Last-Modified` / 条目淘汰 / DevTools 的「禁用缓存」开关决定 —— 引擎无权干预。
- **绘制**：合成器拿一张**已解码的位图**把像素刷上去。

链条是「预加载 →（缓存留不留）→ 绘制能不能立刻拿到」。把预加载等同于缓存，就会得出「只要预载过就一定画得出来」这个错误前提。

| 缓存状态 | 预加载那次传输有没有用 | `block` 靠什么保证不裂图 |
|---|---|---|
| 可用 | 有用：绘制命中缓存、同刻完成 | 释放前的可绘制性探针（0~3ms，玩家无感） |
| 不可用 | **没用**：浏览器把字节丢弃 | 释放前的探针**自己就是那次下载**，遮罩等它完成 |

第二行的代价比「每张都要重下一次」更细：预载那次传输能不能被绘制复用，取决于**预载到显示之间的时间差**。

实测（Fast 3G 200 KB/s，禁用缓存从页面加载起全程生效，girls_orbit_project ch1）：

| 预载 → 显示的间隔 | 该 URL 的请求数 | 观感 |
|---|---|---|
| 0.4 / 9.5 / 14.5 / 15.6 秒（前 4 张背景） | 各 1 条 | 4 张全部「显示前已完成」，转圈圈一次都没出现 |
| 33 秒，且缓存在**预载之后**才被关掉 | 2 条 | 绘制时重新联网；Slow 3G 下等了 15.5 秒（缓存可用时是 0~3ms） |

第一行说明引擎之外还有一层渲染进程内的图片复用，刚取回不久的图即便磁盘 HTTP 缓存被绕过也还能被绘制取到；第二行说明这层复用有时间窗，间隔拉大后就退化成真下载。

所以准确的说法是：**预加载的价值随「预载 → 显示」的时间差衰减**——这正是「窗口秒数」这个参数存在的理由。而无论这一层怎么退化，`block` 的可绘制性探针都保证放行前画得出来；退化只影响玩家等多久，不影响画面是否裂开。

若要在间隔很大时也不重复下载，唯一办法是不依赖 URL 的再次取用，而是**自己持有位图**：把舞台背景从 CSS `url()` 改成常驻的 `<img>` 元素，或走 `fetch → blob → createObjectURL` 后只绘制这份 blob。这属于舞台层的改动，当前未采用，`block` 的保证不依赖它。

**验证口径：勾「禁用缓存」是必测条件，不是可选极端情况。** 缓存可用时，即便引擎没在放行前抓好资源，绘制也能靠磁盘缓存同刻完成、把缺陷整个盖住 —— 只测缓存可用的场景等于没测。禁用缓存的作用正是**去掉「缓存」这一层变量**，让「引擎有没有在放行前把东西抓好」成为唯一可观察的东西。因此 `verify_preload_throttle.js` 提供 `NOCACHE=1`，`verify_preload_paintable.js` 的场景 B 固定启用它。

## 3. 编译期产物：资源清单

`builder.py` 的 `collect_asset_sizes()` 统计「剧本、角色档案与 `theme.json` 中实际被引用的资源路径」的并集及各自体积，内联为：

```html
<script>window.__ASSETS__ = {"images/bg/room.png":{"size":812345,"type":"image"}}</script>
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `size` | number | 文件字节数，取自 `dist/web/` 里实际复制后的文件 |
| `type` | string | `"image"` 或 `"audio"`，由扩展名判定 |

内联而不是独立 JSON 文件，理由与 `window.__SCRIPTS__` 相同：`file://` 下读不到独立 JSON。

缺失时的回退（模板模式或旧产物）：

| 情况 | 处理 |
|---|---|
| `window.__ASSETS__` 不存在 | 按扩展名取缺省体积：图片 800 KB，音频 3.5 MB |
| 某个路径不在清单中 | 同上 |

清单是**全量并集，不按段裁剪**（原因见 §8）。

## 4. 时间模型

### 4.1 每句耗时从哪来

单位是「每条阻塞指令消耗的秒数」，来源按优先级分三级：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 已知模式 | 快进 `lookahead.skipLineSeconds`（0.18），自动 `lookahead.autoLineSeconds`（2.6） |
| 2 | 实测 | 正常模式下最近若干句的相邻推进间隔（EWMA，`α = 0.3`，前 8 句用累计平均） |
| 3 | 缺省 | `lookahead.defaultLineSeconds`（3.0），无样本时使用 |

模式常量必须与 `script.js` 的定时器周期一致（`skipTimer` 180ms、`autoTimer` 2600ms），改动任一侧都要同步另一侧与模板 `info.json`。该一致性由 `test_preload_order.py` 断言守住。

正常模式的实测值直接反映玩家点击节奏，不需要统计鼠标事件，也不需要区分「快速点击」与「正在快进」——后者由 `script.js` 的 `state.skip` 直接给出。

指令的耗时口径：

| 指令 | 计入的秒数 |
|---|---|
| `say` / `narrate` / `title` / `decide` | 一句（`lineSeconds`） |
| `wait` / `pause` 带 `ms` 或 `seconds` | 声明的时长 |
| 裸 `pause`（等玩家点击） | 一句 |
| 裸 `wait` | 0.8 秒（`script.js` 的缺省） |
| 其余非阻塞指令 | 0 |

### 4.2 窗口分档

| 档位 | 条件 | 队列处置 |
|---|---|---|
| T0 | `deadline <= 0`（正在用） | 最前，同时是兜底的候选 |
| T1 | `0 < deadline <= lookahead.windowSeconds` | 高保障区，默认 30 秒 |
| T2 | `windowSeconds < deadline <= lookahead.horizonSeconds` | 远档，默认 180 秒 |
| 不排队 | 超过 `horizonSeconds`，或超出章范围 | 留到下次推进重算 |

T2 的存在是必要的：单曲 4.37 MB 的 BGM 在实测 180 KB/s 下需要 25 秒，而它进入 30 秒窗口时距离被使用只剩 30 秒。只有把远档提前量拉到远超窗口，大音频才可能按时就绪。

### 4.3 分支的时间轴必须分叉

`decide` 的各个选项是**并列**关系，不是先后关系。遍历到 `decide` 时，每个分支都从同一个时间点开始累加；若像 `goto` 那样串行累加，第二个分支的 deadline 会被凭空推迟整个第一分支的时长。

`goto` / `if` 是顺序关系，继续用同一个累加值。`visited` 集合（以 `段名#下标` 为键）用于阻断环。

### 4.4 后台标签页与回溯

| 情况 | 处理 |
|---|---|
| 页面切到后台 | 不采样推进间隔，否则玩家切出去几分钟再回来点一下，会把估计拉到几百秒，窗口塌缩成一句 |
| 单次间隔 < 0.4 秒或 > 20 秒 | 丢弃（连点 / 误触、挂机），不进入平均 |
| 回溯（`rollback`）或读档到章节中部 | 时间轴从新位置重算，`deadline <= 0` 的资源进入 T0，已缓存的直接命中 |

## 5. 调度器

### 5.1 排序依据

每次推进重排待发列表，排序键依次是：

1. **tier 升序**——已过期/正在用的无条件优先，否则当前这一屏的资源会被一直跳过；
2. **slack 升序**——同样紧迫的，越来不及的越先发；
3. **size 升序**——仅用于打破并列。

资源类型**不参与排序**。类型只在两处保留作用：兜底动作不同（见 §7），以及排序键并列时的次级比较。

体积的用法只有一处：`slack = deadline − size / rate`。它决定「还来不来得及」，不决定「谁更重要」。按体积优先会让一首 4 MB 的 BGM 挤掉同一屏的两张背景图，而背景图才是决定画面能否显示的东西。

### 5.2 双队列与单一并发窗口

| 队列 | 用途 | 优先级 |
|---|---|---|
| `bootQueue` | 启动（`boot()`）与进章（`enterStage()`）、兜底（`barrier()`） | 高 |
| `planQueue` | 运行时规划（`hookPredict()`） | 低 |

两者共用一个并发计数，`pump()` 每次先取 `bootQueue`。共用一个窗口而不是各占一个，是为了让「进章时的一整批资源」不会被「运行中的规划」分走连接。

### 5.3 已发起的请求不重排

HTTP 层不提供中途改优先级的能力，因此已经进入下载的资源只能等它跑完。并发窗口是 4，所以最多有 4 项不受重排影响。

仍排在队列里、尚未发起的那部分会被重排：每次 `plan()` 之后，队列重建为「本次规划仍需 + 按新排序键排列」；本次规划不再需要的未发起项被丢弃。

### 5.4 健康度：就绪缓冲秒数

```text
readySeconds = 满足「deadline <= t 的图片资源全部就绪」的最大 t
```

`readySeconds >= windowSeconds` 表示当前窗口已被完整覆盖。音频不作为健康度判据（音频缺失的代价是延迟起播，不是画面缺失）。

## 6. 五个触发点

| # | 触发点 | 调用方 | 时机 | 是否显示遮罩 |
|---|---|---|---|---|
| ① | `boot()` | `index.html` 的 bootstrap | 进入网页、DOM 构造完成后 | 是（`#boot-mask`） |
| ② | `hookPage()` | `engine.js` 的 `showPage()` | 每次切换页面 | 否 |
| ③ | `enterStage()` | `script.js` 的 `start()` / `load()` | 进入舞台前（开始 / 继续 / 读档 / 快读） | 是（`#boot-mask`） |
| ④ | `hookPredict()` | `script.js` 的 `advance()` | 每次剧情推进 | 否 |
| ⑤ | `barrier()` | `script.js` 的 `advance()` 内、`exec(c)` 之前 | 每条指令执行前 | 是（`#wait-mask`，仅 `block` 策略） |

### 6.1 boot()：进入网页

按 `preload.boot` 分级收集，按「加载顺序即优先级」分三级：

| 分级 | 内容 | 是否阻塞揭幕 |
|---|---|---|
| ① 首屏 | `pages.title.background` 与首页 `customButtons` 的 `image` / `hover` | 是 |
| ② 外壳图 | `dialog.background`、`frame.background`、`button.idle` / `button.hover`、`choice.idle` / `choice.hover`、`thumb.placeholder` | 否，后台补齐 |
| ③ 策略附加 | `boot:"system"` → 各启用系统页背景与舞台背景；`boot:"title+story"` → 全部剧情素材 | 否，后台补齐 |

遮罩只等第①级。`boot:"none"` 时不做任何预加载，遮罩立即隐藏。

角色专属对话框**不参与 `boot()`**，原因见 §9。

### 6.2 hookPage()：切换页面

由 `engine.js` 的 `showPage()` 在切换前调用，收集目标页背景后放进队列，不阻塞切换。对应配置 `preload.runtime` 中的 `"page"`。

### 6.3 enterStage()：进入舞台

揭幕前要等的资源分三组。三组的区别是**「等不等得起」**，不是「急不急」：

| 组 | 内容 | 等待方式 |
|---|---|---|
| ① 外壳图 + 首帧关键集 | `theme.json` 声明的外壳图、`deadline <= 0` 的图片、第一个说话/登场角色的专属对话框 | 无条件等满 |
| ② 前奏 | `stage.preludeSeconds` 剧情秒内要用的图片，以及该窗口内其它角色的对话框 | **按下载时间预算截断** |
| ③ 其余 | 规划内剩下的资源 | 不等，揭幕后后台补齐 |

第①组是底线：不能让玩家看到空舞台，也不能让第一句台词出来时对话框还没到。

第②组的选取与等待用了两个不同的口径，缺一不可：

- **选取按剧情秒**（`stage.preludeSeconds`，默认 60）。它回答的是「接下来这么久的剧情要用到什么」，这个问题的答案只能由剧本给。
- **等待按下载时间预算**（`stage.preludeBudgetSeconds`，默认 8 秒，按实测速率折算）。它回答的是「进章前最多让玩家等多久」，这个问题的答案只能由链路给。

只按剧情秒选而不设预算，字节数没有上界：实测某章 60 剧情秒内约 19 MB 图片加 12 张角色对话框，在 Fast 3G 下会让章首遮罩等 95 秒。只按预算选而不看剧情秒，又无从判断哪些资源值得先花掉预算。

预算的累加按 `plan()` 的输出顺序（已是 slack 升序）**逐项累加、超支即切断**，不跳过超支项去捡后面的小文件——顺序即优先级，跳着取会破坏这个性质。并发窗口为 4，因此逐项累加得到的预计耗时是墙钟时间的保守上界。

三组的等待集**不按 `records.done` 过滤**，图片一律走可绘制性探针（§6.5、§2.5）：首帧背景往往在**进网页时**就被 `boot()` 预载过，可能已经是一分钟前，缓存一旦用不上，绘制仍要重新联网。只按 `done` 过滤会出现「遮罩已揭开、玩家看到半张背景」。

遮罩同样有显示延迟（`fallback.maskDelayMs`）：三组资源都在缓存里时探针几毫秒返回，不该让全屏黑幕闪一下。

视野内没有任何可预载资源时不显示遮罩。

对应配置是 `preload.runtime` 中的 `"predict"`：`predict` 关闭时 `enterStage` 直接返回，与「关闭 = 用到才加载」保持一致。

### 6.4 hookPredict()：剧情推进

由 `script.js` 的 `advance()` 在每次推进时调用：`plan()` 从当前位置向前推算，产出待发列表后交给 `applyPlan()` 同步进队列。音效没有特殊优先级——它与其他资源一样按 slack 排队。

### 6.5 barrier()：指令执行前的兜底

放在 `advance()` 的循环里、`exec(c)` 之前，而不是各指令内部：

- `setBg` 同步返回「是否阻塞」，内部用 `state.step` 做 epoch 判断、用 `bgFade` 管理幕布状态。把 `await` 塞进 `setBg` 会改变它的返回语义，并让 epoch 判断与幕布状态机的时机全部错位。
- 「一条指令需要哪些资源」在指令层面是确定的（`bg.src`、`show` 的角色立绘、`music.src`、`sound.src`、`voice.src`、`say.voice`、`say` 的对话框），在 `advance()` 里判断成本极低。

就绪判据分两层，缺一不可：

| 层 | 回答的问题 | 依据 |
|---|---|---|
| 状态记录 | 「这条资源我们发起过没有 / 坏没坏」 | 运行时的 `records`（`pending` / `done` / `failed`），不看它属于哪一段 |
| 可绘制性探针 | 「此刻画不画得出来」 | 真的用一个新的 `Image` 走一次 `load` + `decode` |

**只查状态记录是不够的**：`done` 只说明我们曾经取回过一次，不说明浏览器现在能立刻绘制（原因见 §2.5）。只信它会出现「判据说已就绪、实际背景半张图、且永远不显示遮罩」。

`barrier(c)` 的完整判定：

| 情况 | 处理 |
|---|---|
| 资源已 `failed` | 放行，不等待（等坏资源等于卡死） |
| `fallback` 动作不是 `block` | 不等，只保证「已经发起」，让它在后台慢慢来 |
| `block` | 登记/发起（受并发窗口管理）+ **探针**；等待期间可能亮出 `#wait-mask` |

探针的代价：命中缓存时是「一次内存缓存取用 + 一次解码缓存命中」，实测 0~3 ms；未命中时才真的等网络。因此它对正常游玩没有可感知影响（见 §7.2 的遮罩显示延迟）。

`probeImage` 用 `inflight[]` 持有在途 `Image`，并有 `ASSET_TIMEOUT` 上限——探针本身不会让遮罩永久停留。

无资源可等时返回 `null`，调用方用真假判断即可，不产生多余微任务。

**这是一个硬的任务边界，别的地方不能假设「同一拍里后面的指令会抢在它之前执行」**：`probeImage` 走 `img.onload`，而 load 事件是宏任务——即使命中缓存，`barrier` 的 promise 也不可能同步落地。因此从 `hide X` 到后一条 `show X` 之间，事件循环必然会转一圈。任何「靠 `setTimeout(remove, 0)` 之类的定时器在下一拍之前还没到期」来实现的语义，都必须改成不依赖时序的写法（立绘的同拍折叠就是这样：判定改为前瞻剧本，见 `docs/指令.md` 的 `hide` 一节）。

`advance()` 变异步只为这一个目的。两个并发守卫：

| 守卫 | 作用 |
|---|---|
| `state.barrier` | 等待期间玩家的点击由 `next()` 直接丢弃，不重入主循环 |
| `state.epoch` | 等待可能跨过「退出一局 → 进入下一局」，醒来后确认这条推进仍属于当前这一局 |

## 7. 兜底策略

### 7.1 三档动作

| 动作 | 行为 |
|---|---|
| `block` | 等待该资源就绪，期间显示 `#wait-mask`（转圈 + 字节加权进度 + 可选的「不等了」） |
| `degrade` | 不等。图片保持上一画面或主题兜底背景；音频延迟起播或静音 |
| `missing` | 不等，且不做兜底。背景露出 `body` 默认背景色，立绘不显示 |

默认配置与理由：

| 资源 | 默认动作 | 理由 |
|---|---|---|
| 图片（`bg` / 立绘 / 整屏图 / 对话框） | `block` | 画面缺失是玩家直接看得见的缺陷，且图片体积小（平均 0.79 MB），等待代价低 |
| 音频（`music` / `sound` / `voice`） | `degrade` | 音频占体积的 61%，却不会造成画面缺失；等待它收益最低、代价最高 |

`degrade` 与 `missing` 的区别在实现上是具体的：`.stage-bg` 的主题兜底图由 `theme.js` 写入内联样式，CSS 里还有一层渐变色作为最终兜底。`degrade` 保留这两层（与 `resetStage()` 的复位目标一致），`missing` 需要额外清掉内联兜底，让 `body` 背景色露出来。

兜底是**正确性保证**，调度只影响触发频率：无论排序多精确，都无法保证「玩家推进速度 × 资源体积」始终低于链路能力。调度器的目标是把缺口摊平、减少兜底触发次数；玩家的实际体验由兜底策略决定。

### 7.2 兜底遮罩的界面

| 元素 | 用途 | 与 `#boot-mask` 的区别 |
|---|---|---|
| `#boot-mask` | 进入网页、进入舞台 | 纯黑全屏，遮住一张尚未构造完成的界面 |
| `#wait-mask` | 剧情中途资源未就绪 | 半透明，舞台画面仍可见，转圈居中 |

分开的理由是语义不同：前者遮住的是一张还没画好的界面，后者遮住的是一个已经画好、只差一张图的界面。

进度按字节加权：`已就绪体积 / 待等总体积`。就绪与否以**每一项自己的等待**（探针或加载 promise）为准，而不是以 `records` 为准——后者会在「记录说 done、实际还在等」时把进度显示成 100%。数据全部来自 §3 的清单，不需要任何下载进度事件。

`fallback.allowSkipWait`（默认开）在遮罩上显示「不等了」按钮，点击后该资源按 `degrade` 处理并立即继续，不做全局模式切换。

### 7.3 遮罩的显示延迟

遮罩不是立刻显示的：先等 `fallback.maskDelayMs`（默认 150 ms），超过它还没就绪才亮出来。

原因：绝大多数指令要的资源就在缓存里，探针 0~3 ms 返回；立刻显示再立刻隐藏就是闪一下。150 ms 之后还没好，说明确实在等网络——这时才显示才是准确的信号。

`maskDelayMs: 0` 表示「只要有等待就显示」。它的取值不影响正确性，只影响观感。

### 7.4 快进时的语音

| 配置 | 行为 |
|---|---|
| `fastForward.skipVoice: true`（默认） | `state.skip` 为真时：不预载语音；`say.voice` 与 `voice` 指令不播放语音 |
| `false` | 按正常策略预载与播放 |

语音在快进时通常不会被听完，把它移出队列可以为图片让出带宽。这只影响快进期间，`setSkip(false)` 之后恢复正常；已经因为跳过而未预载的语音在下一次规划中被重新纳入。

判据只有一处（`preload.js` 的 `skipVoiceActive()`），预载侧与播放侧共用，避免出现「不加载但照样播」或「加载了却不播」的不一致。

## 8. 资源归属不能按段推断

编译期清单与运行时规划**都不建立「段 → 资源」的依赖表**，原因有两条：

- 资源被多个段复用。同一个立绘可能在前面十几个段里都出现过，按段组织依赖会让「看起来已经加载过」成为可推断的结论。
- 玩家可以从任意位置进入本章。存档记录的 `seg` / `idx` 可以是章内任意一句，`load()` 从该位置直接调 `enterStage()`。此时「前面的段已经播过」根本不成立，那些资源很可能一张都没下载过。

因此有一条硬规则：

> **判断一个资源是否就绪，唯一依据是它在运行时的真实可用性；不得使用「它在更早的段里出现过」「它在这一局里播过」「我们预载过它」之类的推断来跳过预载。**

落到四处实现：

| 位置 | 要求 |
|---|---|
| 编译期清单 | 记录所有被引用资源的体积，是**全量并集**；不按段裁剪 |
| 运行时规划 | 时间轴一律从传入的 `(seg, idx)` 起算；不查询任何「历史」信息 |
| 兜底判定 | 状态记录只用于「发起过没有 / 坏没坏」，**是否就绪由可绘制性探针回答**（§6.5、§2.5） |
| 章首等待 | 同理：等待集不按 `done` 过滤，图片一律走探针（§6.3） |

同一条规则也覆盖回溯：`rollback()` 退到前面某句时，规划从新位置重算，`deadline <= 0` 的资源进入 T0。

## 9. 章范围与角色对话框

### 9.1 章是搜索上界

| 配置 | 行为 |
|---|---|
| `chapter.scope: "current"`（默认） | 遍历不跨越章边界 |
| `chapter.scope: "all"` | 允许规划到后续章的开头 |
| `chapter.preload: "adaptive"`（默认） | 遮罩只等壳图 + 首帧 + 前奏 |
| `chapter.preload: "complete"` | 遮罩等待目标扩为章内全部可达资源 |

章与章之间的资源缺口由**章首的加载页**承担，不由章末预取承担。一个剧本文件就是一章时，进入新章必然经过 `enterStage()`，因此不需要章末衔接。若作者在同一文件内用嵌套 `chapters` 划分多章，则章与章之间没有独立的加载页，这种情况必须把 `chapter.scope` 设为 `"all"`。

`complete` 不引入第二套等待策略：等待仍走 `waitForPaint`，`timeout` / `onTimeout` 仍是那两个旋钮。追求「全程无缺失」的作者用 `complete` 配合默认的 `onTimeout:"hint"`（`hint` 不下令放行）；愿意到点放行的作者改用 `onTimeout:"release"`。

### 9.2 角色专属对话框：按需而非全量

角色专属对话框（`characters.json` 的 `profile.textbox`）与 `theme.dialog.background` 是同一性质的东西：剧本第一句台词就要出现的界面图。但它的数据源在角色档案里，`collectChrome()` 看不到它。

它**不参与 `boot()`**：十几张、每张约 800KB，玩家还在首页时根本用不到，却会占满连接、把首屏与外壳图挤到队尾——限速下直接表现为「首页长时间空白」。

它按「登场时间」预载：`plan()` 同时产出「角色 id → 首次说话/登场的时间」，`enterStage()` 取前奏窗口内的角色，`barrier()` 取当前指令要用的那个。前奏窗口内可能包含十个以上角色，因此他们的对话框同样受 `preludeBudgetSeconds` 约束——否则十几张图足以吃光整个预算。

## 10. 遮罩与超时策略

### 10.1 遮罩元素

```html
<div id="boot-mask"><div class="boot-spinner"></div><p class="boot-hint" id="boot-hint"></p></div>
<div id="wait-mask" class="is-hidden">
    <div class="wait-panel">
        <div class="boot-spinner"></div>
        <p class="wait-progress" id="wait-progress"></p>
        <p class="wait-hint" id="wait-hint"></p>
        <button type="button" class="paper paper-btn wait-skip">不等了</button>
    </div>
</div>
```

`#boot-mask` 是纯黑全屏遮罩（`z-index:9999`），不读取主题色变量，任意主题下观感一致。`#wait-mask` 是半透明遮罩（`z-index:9990`，低于前者）。两者加上 `is-hidden` 类后渐隐并停止接收指针事件。

两层遮罩各有自己的提示行（`.boot-hint` 与 `.wait-hint`），**`showHint()` / `hideHint()` 两层同时写**。这不是冗余：调用方（`waitForPaint()` / `waitWithBarrier()`）并不知道此刻是哪一层在显示，只写其中一个的后果是实测过的——进章时定时器到点、文字写进了 `#boot-mask` 里的元素，而当时亮着的是 `#wait-mask`，玩家看到的是「等了二十多秒只有一个转圈圈，没有任何文字」。`.wait-hint` 不能复用 `.boot-hint` 的样式：后者的 `position:absolute; bottom:18%` 是相对 `#boot-mask` 定位的，放进 `.wait-panel` 的纵向流里会飘离面板。

### 10.2 三个入口共用一套等待策略

`boot()`、`enterStage()` 与 `barrier()` 的遮罩等待都通过 `waitForPaint(promise)`，行为由 `preload.onTimeout` 决定：

| `onTimeout` | 到 `timeout` 时 | 遮罩何时揭开 |
|---|---|---|
| `"hint"`（默认） | 实测网速，在遮罩上补一行提示文字，**继续等待** | 目标资源真正就绪时 |
| `"release"` | 直接放行 | 到 `timeout` 即揭开，不考虑资源是否就绪 |

`"hint"` 是引擎默认方案，也是模板 `info.json` 写入的取值。

选择 `"release"` 意味着用一个固定秒数赌资源已经就绪。限速条件下赌输的表现就是：遮罩揭开时首页背景还没下载完，玩家看到空白或逐行绘制的画面。`"hint"` 不会露出半成品画面，代价是玩家可能需要在遮罩上多等一会儿——因此补一行文字说明原因。

两种模式都不会无限等待：单个资源的等待上限是 `ASSET_TIMEOUT`（30s，见 10.5），它是内在兜底。

这条兜底对 `"hint"` 有一个必须知道的后果：**等待集里只要有一个资源 30 秒还下不完，遮罩就会在那 30 秒后被放行**，`"hint"` 的「继续等待」不能突破它。若游戏存在「首屏资源在目标网速下需要 30 秒以上」的情形，指望遮罩挡住半成品画面是无效的——此时应当缩减等待集（首帧关键集只放必需项、前奏用 `stage.preludeBudgetSeconds` 截断），而不是调大 `timeout`。

**不要在这三处各自再写一份 `Promise.race`**，否则三处的超时行为会走偏。

### 10.3 实测网速怎么算

`measureSpeedKBps()` 读 Resource Timing，对每个**已完成**的资源算一次单资源传输速率：

```
encodedBodySize / (responseEnd - responseStart)
```

取其中的**最大值**作为「这条链路能跑多快」的估计。返回 `null` 表示没有可用样本（此时按「网络较慢」处理）。

为什么取最大值，而不是「已完成字节总和 ÷ 总耗时」：后者把尚未下载完的请求排除在分子之外，分母却包含它们占用的时间。在「网速正常、资源很大」的场景里（首屏一张 2MB 大图、若干小文件早已完成、大图仍在途），算出来是一个被人为压低的速率，恰好把「资源体积大」误判成「网络较慢」。而「最快的一次传输」只需要一条已完成的资源就能给出链路能力的下界。

三道过滤：

| 过滤 | 原因 |
|---|---|
| 只统计 `transferSize > 0` 的条目 | 命中缓存的资源该值为 0（字节来自磁盘而非网络），耗时又接近 0，计入会得到离谱的速率 |
| 只采信体积 ≥ 8KB 的样本 | 几百字节的响应一次突发就能跑出很高的瞬时速率，不足以代表链路能力 |
| 只采信**最近 10 秒内完成**的样本 | 见下 |

第三条过滤（`SPEED_WINDOW_MS = 10000`）解决的是「中途变网速」：若把限速前的全速传输也算进「最快的一次」，估计值会一直停在限速前的水准（实测会停在 150 MB/s 量级），于是提示文案把「网络较慢」说成「资源体积较大」，预计耗时也全部失真。窗口内没有样本时退回「最近一次采信值」，它超过 60 秒（`RATE_STICKY_MS`）后同样作废，按无样本处理。

这个估计值同时用于「预计下载耗时 = size / rate」，因此与被排进队列的新请求同口径。

`measureSpeedKBps()` 返回的是**实测速率**，不是链路标称带宽：测量时刻预加载队列正按并发窗口（默认 4）同时下载，每条连接只分到链路的一部分，再加上 RTT，实测值会明显低于标称带宽。`preload.slowSpeedKBps` 的阈值因此要按实测值来设。实测标定（本机 CDP 限速，`latency` 60~400ms）：

| 限速设置（标称） | 实测速率 | 默认阈值 250 KB/s 下的判定 |
|---|---|---|
| 100 KB/s（Fast 3G 量级） | 约 35 KB/s | 网络较慢 |
| 500 KB/s（4G 量级） | 约 180 KB/s | 网络较慢 |
| 1000 KB/s（良好 WiFi 量级） | 约 360 KB/s | 资源体积较大 |

即默认阈值把 4G 及以下归为「网络较慢」，家宽 / WiFi 归为「资源体积较大」。可按目标玩家的网络分布调整 `slowSpeedKBps`。

链路上取不到任何样本时（如 `file://`），预计耗时按标称 500 KB/s 折算——这是 `NOMINAL_RATE_KBPS` 常量，只影响排序与章首预算的估算，不影响正确性。

### 10.4 提示文案

文案是引擎级 UI 文字（与 `theme.js` 的 `I18N` 同类），描述的是引擎行为、不随主题与游戏内容变化，因此写死在 `preload.js` 的两个常量里，不放进 `theme.json` / `info.json`。

| 条件 | 文案 |
|---|---|
| 无样本，或实测速率 < `slowSpeedKBps` | 当前网络较慢，加载可能需要较长时间 |
| 实测速率 ≥ `slowSpeedKBps` | 游戏资源体积较大，加载需要更多时间 |

两条文案对应的玩家动作相同（继续等待），区别只在于把等待归因于网络还是归因于游戏体积。

`showHint()` 只负责写入文字与加 `is-shown`，`hideHint()` 只移除 `is-shown`（不清空文字，避免淡出时文字突然消失）。文案由 `hintForNow()` 统一算出（实测网速 → 二选一），`waitForPaint()` 与 `waitWithBarrier()` 都调它，两处的判定与文案因此同源。`showMask()` 会先调用 `hideHint()`，因为同一块遮罩会被 `boot()` 与 `enterStage()` 复用，进舞台时不能残留上一次的提示。

`#wait-mask` 上的提示延迟与该遮罩的显示延迟一致，都是 `preload.timeout`（默认 12s，与启动遮罩同门槛）：兜底等待本身不会因为提示而改变行为（它一律等满，是否放行由 `onTimeout` 与 `fallback.allowSkipWait` 决定），提示只是把「为什么慢」写出来。

### 10.5 单资源等待上限（引擎内部常量）

`ASSET_TIMEOUT = 30000` 是 `preloadImage` / `preloadAudio` 各自的等待上限，**只解除等待、不中止下载**：到点后该资源的 Promise 就 settle，队列继续往下走，请求本身继续下载并进入 HTTP 缓存。

这句话是字面意思，代码必须照做：**超时那一刻不得释放该元素的强引用**。`preloadImage` / `probeImage` 都把「放行等待」（`settle`）与「释放引用 + 摘事件」（`drop`）拆成两个动作，超时只调前者。早期版本的超时函数顺手释放了引用，于是元素只剩事件回调这一条引用（随后也被摘掉），GC 回收它时 Chrome 会**中止在途请求**（Network 面板可见 `ERR_ABORTED`），页面真正用到这张图时再请求一次——表现就是「预加载明明发起过、网速一慢却什么都没留下」，且绘制侧那次重新联网会把幕布留在黑屏上。

有三种状态而非两种：`pending` / `done` / `failed`。等待超时只让 Promise settle，状态保持 `pending`——下载可能仍在继续，晚到的完成事件会把它改成 `done`。这也是兜底判定「已完成才放行」能成立的前提。

它同时是遮罩等待的内在兜底：坏资源最多占用 30s，遮罩不会永久停留。绘制侧另有一个同量级的兜底：`script.js` 的 `decodeImage()` 带 `DECODE_TIMEOUT_MS = 30000`（语义相同，只解除等待不中止下载）——图没有响应时转场照常收尾、幕布照常揭起，露出下层兜底图而不是黑洞。

该常量不开放配置，理由是它判定的不是「慢」而是「坏了」：把它调小（曾用过 8s）会在限速下提前放行队列，队列继续按并发窗口发起新请求，而真正在途的请求并没有减少，于是「限并发保序」形同虚设。

### 10.6 背景转场期间的推进互斥（幕布不会停在满幕）

兜底遮罩解决的是「资源没到就别往下走」；转场解决的是「换图的这段时间画面怎么呈现」。两者有一段交界，处理错了会得到一个与遮罩无关的黑屏：`bg` 带 `transition:"fade"` 时，幕布（`.stage-fade`，纯黑）先落满，再等目标图解码，最后换图并揭幕。

解码这段时间里，`script.js` 的 `bgFade` 必须**已经登记**（`pending: true`，表示转场进行中、新图尚未解码）。若等解码落定才登记，这段时间 `bgFade` 为 `null`，玩家的点击（以及自动 / 快进的节拍）会绕过 `next()` 的转场分支直接推进剧情，`bgSeq` 随之递增 → 本次换图被判定作废 → 幕布停在满幕不动。玩家看到的就是**背景全黑，且越点越黑**。

配套的两件事：

- `next()` 在 `bgFade.pending` 期间**吸收点击**（直接返回）。此刻没有可换的图，放行推进只会作废这次转场；解码通常只有几十毫秒（兜底刚验证过可绘制），点击不会因此「失灵」。解码完成后 `pending` 置回 `false`，点击恢复「立即结束转场并推进一句」的语义。
- 解码有 30 秒上限（`DECODE_TIMEOUT_MS`，见 10.5）。没有它的话，一次无响应的取图会让幕布永远不揭，而 `pending` 又会吞掉所有点击——玩家只能刷新页面。

还有一个容易写成死代码的地方：`advance()` 必须递增 `state.step`。`setBg` 用 `state.step !== step` 判断「解码期间这一步有没有被别处推过（外部 advance / 跳段 / 读档）」，为真时只把图换上并揭幕、不再拦住推进。`state.step` 只声明不递增的话，这个判断永远为假，成为一个看起来有、实际不生效的兜底。

## 11. 调试与验证

### 11.1 运行时观测点

在浏览器控制台可直接读取：

```js
AliceADVPreload.getStrategy()                      // 生效配置（含缺省值兜底后的结果）
AliceADVPreload.plan(script, seg, idx)             // 从 (seg, idx) 起算的待发列表（含 deadline / slack / tier）
AliceADVPreload.readySeconds(script, seg, idx)     // 就绪缓冲秒数（只算图片）
AliceADVPreload.chapterAssets(script, seg)         // 当前章的全部可达资源
AliceADVPreload.getRecords()                       // url → { status, started, keep, size, kind }
AliceADVPreload.probeImage("images/bg/room.png")   // 可绘制性探针（命中缓存几毫秒，未命中等到下载完）
AliceADVPreload.getAssets()                        // 编译期资源清单（路径 → { size, type }）
AliceADVPreload.currentLineSeconds()               // 当前「一句」的秒数（模式常量或实测值）
AliceADVPreload.getDwellSeconds()                  // 实测的每句耗时（无样本时为 null）
AliceADVPreload.measureSpeedKBps()                 // 当前实测速率（KB/s），无样本时为 null
AliceADVPreload.hintForNow()                       // 按当前实测速率会显示哪一句提示
AliceADVPreload.anyMaskVisible()                   // 此刻是否任一遮罩亮着（提示的守卫判据）
AliceADVPreload.assetSize("images/bg/room.png")    // 某资源的体积（清单未命中时为缺省值）
```

`getRecords()` 取代了旧版的 `getCache()`（后者保留为同一张表的别名）：`getCache()` 只记「已发起」，`records` 记三种状态。

要观察「提示有没有出来」，不要只看 `#boot-hint`：两层遮罩各有一个提示元素，`showHint()` 会同时写 `.boot-hint` 与 `.wait-hint`，而它们的 `is-shown` 类别各自独立。判定「玩家此刻看得见哪一句」应该读**当前可见的那层遮罩**里的元素。

但 `status === "done"` 也不等于「现在画得出来」——它只说明我们曾经取回过一次，缓存是否还在不由我们决定（§2.5）。要判断此刻的可用性，用 `probeImage()`。

### 11.2 限速复现

Chrome DevTools → Network → Throttling 选择 `4G` / `Slow 3G`，或自定义下行速率。

**勾上 Network 面板的「Disable cache」是必测条件，不是可选极端情况**（理由见 §2.6）：缓存可用时，即便引擎没在放行前抓好资源，绘制也能靠缓存同刻完成、把缺陷整个盖住。禁用缓存去掉的是「缓存」这一层变量，让「引擎有没有在放行前把东西抓好」成为唯一可观察的东西。

**必须通过 http 打开产物。** CDP 的 `Network.emulateNetworkConditions` 对 `file://` 不生效——文件读取不走网络栈，限速条件无法施加；同时 `file://` 下 `performance.getEntriesByType("resource")` 返回 0 条，测速恒为 `null`。限速相关的问题在 `file://` 下完全复现不出来：

```bash
cd <工程目录>/dist/web && python3 -m http.server 8791
```

推进类验证的节奏要取 2~3 秒/句。以远快于真人的节奏（例如 700ms/句）推进会让验证脚本跑赢预加载器，报出大量「用到才下」——那是节奏问题，不是引擎问题。

`verify_preload_barrier.js` 刻意把 `lookahead.windowSeconds` / `horizonSeconds` 压到 1 秒：运行时规划因此几乎为空，每个新资源都只能由兜底自己临时下载，必然来不及。三个场景的推进深度会明显分化（`block` 更慢），这个分化本身就是「兜底真的在拦停」的证据。

`verify_preload_paintable.js` 的场景 B 必须用 `Network.setCacheDisabled(true)` 才能复现：只限速而不禁用缓存时，缓存命中的请求同刻完成，看不出问题。
